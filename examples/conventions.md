# SQL writing conventions

These conventions apply to SQL Server.

## Writing style

- SQL is written in **lower case**, keywords included: `select`, `from`, `where`, `join`. This also
  applies to generated SQL.
- Every identifier uses **snake_case**, and is explicit: clarity comes before brevity. Abbreviations
  such as `usr`, `dt` or `lbl` are avoided.
- An `insert` always names its columns.

  ```sql
  -- Yes
  insert into sales.invoices (invoice_number, customer_id, issued_on)
  values (@invoice_number, @customer_id, @issued_on);

  -- No
  insert into sales.invoices
  values (@invoice_number, @customer_id, @issued_on);
  ```

- A `bit` column is compared explicitly: `where is_active = 1`.

## Naming

Tables are named in the **plural**: `sales.invoices`, `sales.invoice_lines`.

Every constraint, index and default is **named explicitly**. A name left to the engine is generated,
different on every database, and cannot be referred to in a migration script.

| Prefix | Object |
| --- | --- |
| `pk_` | primary key, named `pk_{table}` |
| `fk_` | foreign key |
| `ck_` | check constraint |
| `uq_` | unique constraint carrying a business rule |
| `ux_` | unique index with a technical or performance purpose |
| `ix_` | index |
| `df_` | default value |

The difference between `uq_` and `ux_` is intentional. A `uq_` says something about the business: two
invoices cannot share a number. A `ux_` says something about the implementation: this lookup must be
fast and unique.

SQL Server stores a default value as an object of its own, which is why defaults have a prefix too.

## Keys

Unless told otherwise, every table has a **surrogate key**: an integer generated by the engine, with no
business meaning. That key is the primary key of the table, and relations between tables use it.

```sql
invoice_id bigint not null identity (1, 1),
constraint pk_invoices primary key (invoice_id),
```

A natural key, such as an invoice number, remains a column with a unique constraint:

```sql
constraint uq_invoices_invoice_number unique (invoice_number),
```

When the rows of a table leave the database — exposed through an API, or imported and exported between
databases —, the table also carries a **public identifier**, a GUID. An `identity` value differs from
one database to another; the GUID stays the same for the same row, wherever it goes.

```sql
invoice_unique_id uniqueidentifier not null
    constraint df_invoices_invoice_unique_id default newid(),
```

```sql
create unique index ux_invoices_invoice_unique_id on sales.invoices (invoice_unique_id);
```

- it is the only identifier exposed outside the database;
- it is never used in a foreign key.

## Types

### Strings

The business limit of a string is carried by its **type**: `nvarchar(64)`, `nvarchar(200)`. A `check`
only expresses what the type cannot say, such as a minimum length.

```sql
code  nvarchar(64)  not null,
label nvarchar(200) not null,
constraint ck_payment_terms_code_len check (len(code) >= 1),
```

`nvarchar(max)` is kept for text that really has no limit. It is a different type from `nvarchar(n)`:
its value is stored outside the row when it grows, and it cannot be a key column of an index, whose key
is limited to 1,700 bytes.

`len()` ignores trailing spaces, which is the expected behaviour here: a label made of spaces is empty.

### Numbers

| Use | Type |
| --- | --- |
| amounts | `decimal(18, 2)` |
| quantities, unit prices, rates | `decimal(18, 6)` |

`float` and `real` are not used for business values. They are approximate by nature, and an amount must
add up exactly. They remain acceptable for scientific or statistical data, when that context is
explicit.

### Dates and times

A point in time is stored as `datetimeoffset(3)`, with `sysdatetimeoffset()` as its default. The offset
keeps the moment unambiguous whatever the time zone of the server.

### Booleans

A boolean is a `bit`. The type holds nothing else, so a `check (col in (0, 1))` would add nothing.

## Nullability

Columns are **not null by default**. `null` complicates predicates, sorting, comparisons and joins, and
avoiding it by default keeps the model and its queries simpler.

`null` is used only when it carries a business meaning, or when it is structurally natural, such as an
optional foreign key.

- **Text columns** prefer an empty string `''` to `null`. `null` is kept for the rare case where the
  difference between "unknown" and "known to be empty" matters to the business.
- **Date columns** use `null` for the absence of a value: a date not yet known, or not applicable.

A `check` that evaluates to `null` is not a violation. Writing `col is null or …` at the start of a
`check` therefore adds nothing.

## Comments in code

A comment says what the code does not say by itself: the reason for a choice, a trap, a rule the code
enforces. It does not repeat the next line. It is written in the language the team works in.

## Scripts

- A script is split into batches by `go`. `go` is not a T-SQL statement: SSMS and `sqlcmd` split on it,
  and some statements must open their own batch.
- DDL is transactional in SQL Server. A migration runs in a transaction, and a script that fails
  halfway leaves nothing behind.

## When the rules do not decide

When several implementations are valid and these rules do not choose between them, stop and ask rather
than pick one. For example:

- two constraints that might conflict;
- a column whose business meaning is unclear: does a `null` really carry a meaning, or should it be an
  empty string?
